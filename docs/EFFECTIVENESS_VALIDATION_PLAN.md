# ontoMeta 有效性验证方案（对外价值证明版）

> 目标读者：需要被说服的人——投资/立项评审、潜在客户的数据负责人。
> 因此本方案的主轴是**「基于本体的问数，比不基于本体的问数强多少」**，而不是功能验收。
> 每个结论都要求有对照组、有金标准、可复算。

---

## 0. 要证明的四条声明（可证伪）

| # | 声明 | 证伪条件 |
|---|---|---|
| S1 | 零注释、零外键的存量 ERP 元数据，能自动升维成可用的业务本体 | 对象识别 F1 < 0.70（L2 档） |
| S2 | 本体能正向生成物理数仓并真跑出数 | 四类制品任一环节落不出正确行数 |
| S3 | **跨系统问数，有本体能答、没本体答不了** | 跨系统档 B2 相对 B1 领先 < 40 个百分点 |
| S4 | **宁可拒答不可错答**的定位站得住 | 错答率 > 2% |

S3 是本方案的**主命题**，S4 是**一票否决项**。S1/S2 是支撑，不是卖点。

---

## 1. 选型

| 维度 | 选择 |
|---|---|
| 行业 | 消费品分销 / 零售连锁 |
| 主业务系统 | **ERPNext（Frappe）**——即现有 DataHub 中那 734 张表 |
| 副业务系统 | **Odoo**（`crm` + `sale` + `website_sale`），扮演「前端营销/电商系统」 |
| 业务场景 | **O2C 订单到现金**：下单 → 库存分配/出库 → 开票 → 回款 → 应收账龄 |

**为什么是双系统。** 单系统只能证明 S1/S2，那是「元数据工具」的价值，说服力有限——客户会问"我直接让 LLM 读 schema 写 SQL 不行吗"。只有当同一业务对象在两个系统里物理形态完全不同（`tabCustomer` vs `res_partner`、`Item` vs `product_template`、两套状态机），本体作为**跨系统语义中间层**的不可替代性才成立。S3 就是为回答这个质疑设计的。

**为什么副系统选 Odoo 而不是电商 demo 库。** 唯一理由：Odoo 的语义模型是**机读**的（见 §2）。换成 Saleor/自建库，跨系统档就只能人工判卷，样本一少结论就不可信。业务上讲得通——ERP 管后端履约、另一套系统管获客与线上下单，是常见集团架构。

**验证范围收敛**：O2C 链路核心 40 张表 + 周边 60 张，其余作噪声，不要贪多。

## 2. 金标准：机读 + 一次人工净化

### 2.1 两个系统都自带语义模型

| 系统 | 元数据表 | 提供的金标准 |
|---|---|---|
| Frappe | `tabDocType` / `tabDocField` | `fieldtype='Link'` → 真外键；`label` → 业务中文名；`istable=1` → 明细行表（不该判为独立业务对象）；`name` 列 → 真实主键 |
| Odoo | `ir_model` / `ir_model_fields` | `ttype ∈ {many2one, one2many, many2many}` + `relation` → 关系方向与基数 |

**这几张表必须从喂给 ontoMeta 的输入里排除**，只作评分答案。做法：DataHub 采集时按表名黑名单过滤，并在验证开始前用 `--check-leak` 复核一遍本体输入集。金标准泄漏一次，全部分数作废。

抽取脚本：[extract_gold_ontology.py](../backend/scripts/extract_gold_ontology.py)

```bash
cd backend && source .venv/bin/activate
python -m scripts.extract_gold_ontology --system frappe \
  --dsn mysql+pymysql://root:pwd@127.0.0.1:3306/_erpnext --out ../benchmark/gold_frappe.json
python -m scripts.extract_gold_ontology --system odoo \
  --dsn postgresql+psycopg2://odoo:pwd@127.0.0.1:5432/odoo --out ../benchmark/gold_odoo.json
```

输出直接采用 ontoMeta 自己的受控词表（`business_object`/`data_table`/`bridge`、四种基数、六种语义类型），打分是同口径比较，不需要再做映射。

### 2.2 必须做的人工净化（约 1 人日）

Frappe/Odoo 的元数据是**框架级**模型，不是人工策划的业务本体。直接当答案用，分数是假的。至少要处理：

- **框架字段**：`owner`/`modified_by`/`docstatus`/`idx`/`_comments` 等每张表都有，脚本已打 `is_framework=true`，评分时从分母剔除。
- **技术性 Link**：指向 `User`/`Role`/`File` 的外键不是业务关系，需人工剔除或降权。
- **`Dynamic Link`**（多态外键，无静态目标）脚本落在 `unscoreable[]`，打分时从分母剔除——不要算作漏召回。
- **模块归属边界**：`Contacts`/`Geo` 模块里的 `Contact`/`Address` 是业务对象，`Core`/`Desk`/`Website` 是框架噪声。脚本按模块名判定，边界表需人工确认。

净化后冻结为 **`gold_v1`**，后续不得因为跑分难看而回头改金标准。改了要记 changelog 并重跑全部对照组。

### 2.3 已知会被金标准照出来的问题

`Frappe 的主键恒为 name 列`，而当前主键推断只认 `<对象>_id`/`id` 约定，必然大面积漏判。这不是 bug，是**约定假设在真实系统前失效**——benchmark 的作用就是把这类问题从"感觉不太行"变成"L2 档主键识别率 12%"。预期还会照出：明细行表被误判为独立对象、`Table` 字段无物理列却被当属性。

## 3. 验证设计

### 3.1 主轴 C：Data Agent 问数（重头，占 60% 工作量）

**50 题**，每题配一份手写金标准 SQL 与答案值：

| 档 | 题量 | 说明 | B1（无本体）预期 |
|---|---|---|---|
| 描述型 | 15 | 单表/单系统取数："上月华东区销售订单金额" | 大概率能答 |
| 分析型 | 25 | 多表 JOIN + 口径："DSO 应收周转天数按客户分组 Top10" | 口径易错 |
| **跨系统** | **10** | 必须同时落到两个系统 | **预期大面积失败** |

跨系统 10 题示例（这 10 题是全案的胜负手）：

1. 线上渠道下的单，有多少在 ERP 里最终没开票？
2. 同一客户在两个系统里的应收合计是多少？（客户主数据重复）
3. 电商 SKU 销量 Top10，在 ERP 里各自的库存周转天数？（SKU 与 Item 粒度差）
4. 哪些客户线上频繁下单、线下却从未回款？
5. 两套"已完成"口径不一致导致的订单数量缺口有多大？

其余 5 题围绕状态机映射与退货/部分发货展开。

### 3.2 对照组（缺了就不叫价值证明）

| 组 | 设置 | 证明什么 |
|---|---|---|
| **B0** | 资深数据架构师手工建同样 100 张表的模型，记录耗时 | 效率（人日 → 小时） |
| **B1** | LLM 直接吃物理 schema 出 SQL，无本体 | **本体的增量价值** |
| **B2** | ontoMeta 全流程 | —— |

B1 必须给足公平条件：同一模型、同样的重试次数、schema 全量可见。**赢得不体面，结论就不可信。**

### 3.3 轴 A：本体质量（压成两档，作为 S1 支撑）

| 档 | 设置 | 用途 |
|---|---|---|
| **L2**（主）| 去约束、去注释——即当前真实 DataHub 形态 | 客户数据的真实起点 |
| **L1**（上界）| 保留注释与约束 | 量化"投资元数据治理能换到多少提升" |

L1 与 L2 的差值本身是一句可售卖的结论："把注释补齐，对象识别能从 0.72 提到 0.87"。

**L3 全码化**（表名 `T_SA_ORD01`、字段 `CFLDA03`，模拟用友/金蝶）列为**可选压力档**，跑了就写进附录——**哪怕结果难看也不删**。它回答的是"最坏情况能不能用"，迟早会被问到。

### 3.4 轴 B：工程闭环（降级为门槛项，不占篇幅）

四类制品（materialize/sync/transform/metric）在 O2C 链路上各跑通一次，验收即通过，不做精细打分。**它是 S3 的前置条件**——没有真数据落地，问数无从谈起。唯一要专门验的是负例：故意断开源库，回执必须 `state=failed` 而不是假绿。

## 4. 验收阈值

**主命题（S3）**
- 跨系统档：B2 正确率 ≥ 70%，且相对 B1 领先 **≥ 40 个百分点**
- 全 50 题：B2 ≥ 80%，相对 B1 领先 ≥ 25 个百分点

**一票否决（S4）**
- **错答率 ≤ 2%**（给出了答案但与金标准不符）
- 拒答率 ≤ 20%；首答 P50 ≤ 20s

**支撑项（S1/S2）**
- 对象识别 F1：L2 ≥ 0.70，L1 ≥ 0.85
- 框架噪声表误判为业务对象 ≤ 5%
- 关系召回 ≥ 0.70；已召回关系的方向+基数正确率 ≥ 0.85
- 连跑两次，对象/属性/关系 diff = 0
- 建模工时：B2 ≤ B0 的 30%
- 四类制品各跑通一次，行数与手写 SQL 一致；断源时回执 `state=failed`

## 5. 排期与交付物（3 周）

| 周 | 内容 |
|---|---|
| W1 | 起 ERPNext + Odoo 并灌 3 个月单据（含退货/部分发货/坏账等脏案例）；跑金标准抽取 + 人工净化冻结 `gold_v1`；写脏化脚本 |
| W2 | **50 题问题集与金标准 SQL**（最费人力，尽早开工）；轴 B 四类制品打通；轴 A 跑 L1/L2 |
| W3 | 三组对照实盘；出报告与价值陈述页 |

**交付物**
1. `benchmark/` 套件：`gold_v1` JSON + 脏化脚本 + 打分脚本 + 50 题集与金标准 SQL
2. 《有效性验证报告》：四条声明逐条结论 + 对照组数据
3. **一页价值陈述**：建模工时 B0→B2 对比；跨系统问题从"做不了"到 N% 可答——这页是真正拿出去讲的东西

**把打分脚本接进 CI。** 一次性验证只值一份报告；沉成回归基线后，以后每次动 prompt、改分类器、调关系推断都能立刻看出涨跌。这是这三周投入唯一能持续复利的部分。

## 6. 风险与诚实条款

- **金标准净化不做，分数就是假的**（§2.2），1 人日省不得。
- **demo 数据太干净**：ERPNext 官方样例单据量小、链路残缺，必须补造退货、部分发货、坏账等脏案例，否则 O2C 指标验不出真问题。
- **B1 可能不像预期那么弱**。若跨系统档 B1 表现良好，说明本体在此场景未产生不可替代价值——**如实写进报告并重新审视定位**，不要靠削弱 B1 来赢。
- **L3 若崩盘**，结论应是"无注释的国产 ERP 需先做术语补录"，而不是下调阈值。
- 跑分难看时改金标准 = 自欺。改动须记 changelog 并重跑全部对照组（§2.2）。
